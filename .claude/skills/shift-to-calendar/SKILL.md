# シフト表 → Googleカレンダー反映

シフト表の画像から対象者の1か月ぶんを抜き出し、Googleカレンダーに終日予定として登録する。
毎月のシフトが出たら「カレンダーに反映して」の一言で回るように作られている。

## 設定

この設定は毎回そのまま使う。変更したいときはこのセクションを書き換えれば次回から反映される。

| 項目 | 値 |
| --- | --- |
| 反映先カレンダー | `libe.skillupkobo.hateruma@gmail.com`（表示名「スキルアップ工房スタッフ_波照間」） |
| タイムゾーン | `Asia/Tokyo` |
| 対象者（シフト表の行名） | `みだい` |
| 同期マーカー | 予定の説明欄に `[shift-sync]` を入れる |
| 再実行時 | 同じ月の `[shift-sync]` 付き予定を削除してから作り直す |

対象者が設定と違う人だとユーザーが言った場合は、その回だけその人を対象にする（設定は書き換えない）。
「全員分」と言われたときは下の「全員分を登録する場合」に従う。

### 勤務日の予定

| 項目 | 値 |
| --- | --- |
| タイトル | セルの文字そのまま（`事業所` / `在宅` / `VO` / `VO（叶内）` / `在宅/事業所`） |
| 終日 | `allDay: true` |
| 表示 | `AVAILABILITY_FREE`（予定なし） |
| 色 | 指定しない（カレンダーの既定色） |
| 通知 | 指定しない |

終日の勤務予定を「予定あり」にすると、共有カレンダーで空き時間を探している人から
その日が丸一日埋まって見えてしまうので、勤務日は `FREE` にしている。

### 休みの予定

| 項目 | 値 |
| --- | --- |
| タイトル | `【私用】予定あり（終日返答遅くなります）` |
| 終日 | `allDay: true` |
| 表示 | `AVAILABILITY_BUSY`（予定あり） |
| 色 | 指定しない（カレンダーの既定色） |
| 通知 | `overrideReminders: [{ "method": "popup", "minutes": 420 }]` |

休みは逆に `BUSY` にする。共有カレンダーを見た同僚に「この日は捕まらない」と伝えるのが目的だから、
空いているように見えては意味がない。

`minutes: 420` は「前日の午後5時」。終日予定の通知はその日の 0:00 からの分数で数えるので、
前日17:00 = 7時間前 = 420分になる。時刻で直接指定はできない。

色はどちらの予定にも付けない。カレンダーの既定色のままにしておくのがユーザーの希望で、
個別に色を付けると本人が色分けに使っている意味と衝突してしまう。
もし過去に色を付けた予定を既定色に戻す必要が出たら、`update_event` に `colorId: "0"` を渡す。
空文字や未指定では消えず、`0` だけが「色なし」として通る。

休みであることをそのまま書かず `【私用】` としているのは、共有カレンダーに私生活の情報を
載せないための言い回し。ユーザーが別の文言を指定しない限りこのタイトルを変えない。

## なぜこの手順なのか

シフト表は横に長い表で、1枚のスクリーンショットに収まらず前半・後半に分かれることが多い。
このとき一番起きやすく、一番気づかれにくい事故が **列と日付が1つズレたまま丸ごと登録されること** だ。
ズレても予定はそれらしく入ってしまうので、本人がカレンダーを見ても気づけない。

だから、画像から直接カレンダーに書き込むことは絶対にしない。
一度「日付 → セルの中身」の一覧データに落とし、曜日の突き合わせで機械的に検算してから書き込む。
検算スクリプトはそのために用意してある。

## 手順

### Step 1. 画像を受け取る

シフト表の画像が添付されていなければ、ここで止めて画像を出してもらう。
前月のシフトを勝手に使い回したり、記憶で補完したりしない。

複数枚（前半・後半など）に分かれている場合は全部揃っているかを先に確認する。
1日から月末までが画像のどこかに必ず写っている必要がある。

### Step 2. 表の構造を読む

まず対象月と日付ヘッダーを確定させる。

1. 年月を読む（例：`2026年 10月`）。画像に無ければユーザーに聞く。
2. 日付行（`1 2 3 …`）と曜日行（`木 金 土 …`）を、列記号（`B` `C` `D` …）とセットで書き出す。
   列記号まで控えるのは、後で対象者の行を追うときの座標になるからだ。
3. 対象者の行（設定では `みだい`）を左端の名前列で探す。同じ列に他のスタッフ名が並んでいるので、
   行の高さを目で追って隣の行と取り違えないようにする。

### Step 3. 日付ごとのセルを書き出す

対象者の行を、**その月の1日から末日まで1日も飛ばさずに** 読み取り、
`/tmp/claude-shifts.json` に次の形式で保存する。

```json
{
  "year": 2026,
  "month": 10,
  "person": "みだい",
  "calendar_id": "libe.skillupkobo.hateruma@gmail.com",
  "days": [
    { "date": "2026-10-01", "weekday": "木", "cell": "VO",        "action": "work" },
    { "date": "2026-10-02", "weekday": "金", "cell": "",          "action": "off"  },
    { "date": "2026-10-05", "weekday": "月", "cell": "休",        "action": "off"  },
    { "date": "2026-10-26", "weekday": "月", "cell": "VO（叶内）", "action": "work" }
  ]
}
```

- `weekday` は **カレンダーから計算した曜日ではなく、シフト表の画像に書いてある曜日** をそのまま写す。
  計算値を入れてしまうと検算が素通りしてしまい、ズレを見つけるという唯一の目的が失われる。
- `cell` は見たままの文字。`VO（叶内）` のような括弧書きも、`在宅/事業所` のようなスラッシュも省略しない。
  セルが空欄・グレーなら空文字にする。
- `action` は `休`・空欄・グレーなら `off`、それ以外は `work`。
- 月の全日を必ず入れる。飛ばした日があると、画像の撮り漏れなのか本当に空欄なのか区別できなくなる。
- 表の右端に休み日数の集計列（`9日` など）があれば `expected_off_days` に入れる。
  曜日チェックは列のズレしか見つけられないが、この件数照合は
  「勤務日と休みを取り違えた」タイプの読み違いを拾ってくれる。別の角度からの検算になる。

全員分を登録する場合は、`person` / `days` の代わりに `people` を使う。中身は同じ形。

```json
{
  "year": 2026,
  "month": 10,
  "calendar_id": "...",
  "people": [
    { "name": "つむり", "expected_off_days": 9, "days": [ ... ] },
    { "name": "タキ",   "expected_off_days": 9, "days": [ ... ] }
  ]
}
```

### Step 4. 検算する

```bash
python3 .claude/skills/shift-to-calendar/scripts/validate_shifts.py /tmp/claude-shifts.json
```

このスクリプトは、曜日の不一致・日付の重複や抜け・月外の日付を検出する。
エラーが出たら、それは読み取りミスであってスクリプトの誤りではない。画像を読み直してJSONを直す。

特に「曜日が1日分ズレている」というエラーがまとまって出たら、列を1つずらして読んでいる。
どこからズレ始めたかを見て、その列から読み直す。

### Step 5. ユーザーに確認を取る

検算が通ったら、登録内容を表にして見せる。カレンダーへの書き込みはユーザーの了承を得てから行う。
他人と共有しているカレンダーに入るので、勝手に確定させない。

勤務日の一覧と内訳（`事業所` 何件、`VO` 何件…）、休みの日付を並べて出す。
件数を添えると、ユーザーが自分の感覚と突き合わせやすい。
画像が不鮮明で読み取りに自信がないセルがあれば、その日付を名指しで伝える。

### Step 6. 既存の同期済み予定を消す

同じ月を何度反映しても増殖しないように、先に前回ぶんを消す。

1. `mcp__Google_Calendar__list_events` で対象カレンダーの対象月を取得する
   （`startTime` は月初、`endTime` は翌月初、`timeZone` は `Asia/Tokyo`、`pageSize` は 250）。
2. 説明欄に `[shift-sync]` を含む予定だけを `mcp__Google_Calendar__delete_event` で削除する。
3. マーカーの無い予定は **絶対に消さない**。定例MTGなど、ユーザーが手で入れた予定が混ざっている。

削除した件数はあとで報告するので数えておく。

### Step 7. 予定を作る

`mcp__Google_Calendar__create_event` を、上の「勤務日の予定」「休みの予定」の設定どおりに呼ぶ。
共通の引数は次のとおり。

| 引数 | 値 |
| --- | --- |
| `calendarId` | `libe.skillupkobo.hateruma@gmail.com` |
| `startTime` | その日（例 `2026-10-01`） |
| `endTime` | 翌日（例 `2026-10-02`）※終日予定の終端は排他的なので、当日を入れると0日間になる |
| `timeZone` | `Asia/Tokyo` |
| `description` | `[shift-sync] 2026年10月シフト（みだい）より自動登録` |

独立した予定なので、作成は並列に呼んでよい。1か月ぶんで30件前後になる。

### Step 8. 報告する

- 登録した件数（勤務日・休みの内訳つき）と対象月
- 削除した既存の同期予定の件数
- 読み取れなかった・判断に迷ったセルがあれば、その日付と理由

迷ったセルを黙って落とさない。勤務日が1日抜けるのは本人にとって実害がある。

## 全員分を登録する場合

「全員分」と言われたときは、対象者ひとりではなく表に載っている全スタッフを登録する。
基本の手順は同じで、次の点だけ変わる。

| 項目 | 全員分のとき |
| --- | --- |
| タイトル | `名前：セルの文字`（例 `つむり：事業所` `Knight：VO（戸田）`） |
| 休み | 登録しない（勤務日だけ） |
| 表示 | `AVAILABILITY_FREE` |
| 同期マーカー | `[shift-sync:all]`（ひとり分の `[shift-sync]` と混ざらないように分ける） |

名前を頭に付けるのは、1日に6人ぶんの予定が並ぶので、誰の予定かがタイトルの先頭で
読み取れないと一覧として役に立たないため。

休みを登録しないのは件数の問題。6人×31日を全部入れると月186件になり、
カレンダーが埋まって肝心の「誰が出ているか」が読み取れなくなる。
勤務日だけなら月132件で、その日に名前が無い人が休みだと分かる。

マーカーを `[shift-sync:all]` と分けておくのが大事で、これが同じだと、
ひとり分を作り直したときに全員分まで巻き添えで消える。
削除するときはマーカーを完全一致で見て、自分が作った側だけを消す。

## セルの読み方

このシフト表で出てくる記号：

| セル | 意味 | 扱い |
| --- | --- | --- |
| `事業所` | 事業所勤務 | 勤務日 |
| `在宅` | 在宅勤務 | 勤務日 |
| `VO` | VO対応 | 勤務日 |
| `VO（叶内）` `VO（戸田）` | 担当者名つきVO | 勤務日。括弧ごとタイトルにする |
| `在宅/事業所` | 両方 | 勤務日。そのままタイトルにする |
| `休` | 休み | 休み |
| 空欄・グレー | 休み | 休み |

**空欄・グレーのセルは「未定」でも「情報なし」でもなく、休みを意味する。**
表の上では `休` と書かれた日とグレーの日が混在するが、カレンダー上はどちらも同じ
`【私用】予定あり（終日返答遅くなります）` になる。ただし報告のときは区別して伝えると、
ユーザーが元の表と突き合わせやすい。

知らない記号が出てきたら、勝手に解釈せずユーザーに意味を聞く。
新しい記号だと分かったらこの表に追記しておくと次回から迷わない。

## つまずきやすいところ

- **画像が前半・後半に分かれている**：境目の日付が両方に写っていたり、逆に片方にしか写っていない列がある。
  日付単位で突き合わせれば重複は自然に解消できる。検算の「抜け」エラーは撮り漏れのサイン。
- **月末が30日か31日か**：2月や30日までの月で末日を間違えやすい。検算が拾う。
- **左端の名前列が横スクロールで隠れている**：後半の画像で名前列が見えない場合、
  行の並び順（上から何番目か）を前半の画像と対応させる。順番は変わらない。
- **グレーのセルに引きずられる**：表の見た目ではグレーは「何もない」ように見えるが、休みである。
  読み飛ばさずに `off` として1日ぶん必ず記録する。
